## #1448 / #1449 portfolio kill-switch latch ownership review — `risk.go`

**#1448** the portfolio latch is owned by ONE signal per cycle: `equityGuardArmed := equityAvailable && prs.PeakValue > 0` (evaluated AFTER the peak ratchet, so any cycle with a positive `totalValue` arms it in the same call); armed ⇒ the latch trips on `equityDD > MaxDrawdownPct` ONLY and `Source` is always `"equity"`; not armed ⇒ it trips on `marginDD > MaxDrawdownPct` and `Source` is always `"margin"`. `PeakValue == 0` is folded into "not armed" deliberately rather than kept as a third case: it means no equity snapshot has EVER been recorded, which is the same "the equity guard cannot measure" condition as a pooled wallet with no trustworthy balance, and it preserves cold-start protection verbatim. The margin-wins tie-break is gone — the two arms are mutually exclusive, so no tie can exist. **Why:** the latch force-closes the whole book (including `manual` and spot positions that contribute nothing to the margin ratio, `AggregatePerpsMarginInputs` counts `type == "perps"` only) and holds it until an operator resets, while the two signals diverge exactly when deployed margin is a SMALL share of the book — there the avertable loss is bounded by that small margin and the latch cost is the full book. Live incident 2026-08-22: 65.3% margin drawdown on $48.42 of margin latched the fleet at 9.8% equity drawdown against a 30% limit, closing an ETH position still above its configured SL floor and a flat-PnL manual BTC position. Per-POSITION margin protection is unchanged and stays with the #292 per-strategy circuit breaker in `CheckRisk` (same ratio, force-closes that one strategy on a cooldown, no latch). **Warn band:** structurally unchanged (`marginWarn = marginDD > warnDrawdownPct`, `source="margin"` event labeling, all `WarningSent`/`WarnBandEnteredAt`/`LastWarning*DDPct`/`Warning*DeltaPct` bookkeeping identical), except that `marginDD` above `MaxDrawdownPct` is now a REACHABLE warn state and gets its own reason wording — "exceeds limit … portfolio latch governed by equity drawdown … per-strategy circuit breakers own margin protection (#1448)" instead of the false "approaching". `BuildPortfolioWarningMessage` renders the margin figure as `perps margin X% from limit`, no longer as a distance to the kill switch, because the warn DM never renders the reason string and that label was the only operator-facing text on this path.

**#1449 review — untrusted equity is a THIRD state, not "unavailable":** `pooledEquityComplete` says the total EXISTS; it does not say it is trustworthy. `computeSubsetPortfolioValue` sets `usedPVFallback` when a fully-contained NON-pooled shared wallet's balance fetch fails and the total substitutes `sum(member PV)`, and `resolveSharedWalletRiskBalances` sets `usedStale` for a one-generation-old balance — both leave `pooledEquityComplete == true`. The call site now also passes `equityTrusted = pooledEquityComplete && !usedPVFallback && !usedStaleRiskBalance`. The latch **stays with equity** on those cycles by design: `sum(member PV)` prices every position at the same live marks and a one-generation-old balance is a real balance, so equity still measures real book loss — and handing the whole book to the margin signal over a transient balance-fetch blip is precisely the #1448 failure. What an untrusted total must never do is make a drawdown DISAPPEAR, so two things gate on `equityTrusted` instead: (1) the peak ratchet is skipped inside the risk check (the caller's post-hoc rollback stays as belt-and-braces, but `CurrentDrawdownPct` is no longer written off a peak the caller is about to undo), and (2) `equityDD` is FLOORED at `priorEquityDD` (the `CurrentDrawdownPct` read before anything this cycle overwrites it). Monotone across a run of untrusted cycles; the first trusted cycle overwrites with a real measurement. **The floor can never itself latch**, because `priorEquityDD` is CLAMPED to `cfg.MaxDrawdownPct` while the latch test is a strict `>`. The clamp is load-bearing and replaces an earlier, WRONG soundness argument ("every stored reading came from a cycle that did not latch, so it is at or below the limit"): `CurrentDrawdownPct` is written BEFORE the latch check, so the latching cycle persists its OVER-LIMIT measurement and `db.go` writes it to SQLite. Both auto-reset paths cleared it, but the #1368 owner-DM reset cleared only `KillSwitchActive`/`KillSwitchAt`, so the first post-reset untrusted cycle floored a healthy measurement back up to the stale over-limit value and re-latched the whole book off a number nothing measured that cycle (a plain restart reaches the same state). The clamp is applied at READ time, never stored, so a `MaxDrawdownPct` change re-derives it instead of truncating the record; a non-positive limit yields a non-positive floor, which cannot raise a drawdown already floored at 0. A genuine this-cycle measurement above the limit is NOT clamped and still latches, so the clamp is not a fail-open. `ResetPortfolioKillSwitchManual` (risk.go) is the second half of the fix and the sole body of the DM reset: it clears both drawdown readings and the substituted marker alongside the latch flags — matching `ClearLatchedKillSwitchSharedWallet` and `AutoResetConfirmedFlatKillSwitch` — and RETURNS the pre-reset reading so the `reset` audit event still records it. It deliberately does NOT re-baseline `PeakValue`: a manual reset makes no claim that the book is flat or the total verified.

**#1449 review — the floored reading is persisted and therefore MARKED:** `CurrentDrawdownPct` carries the floored decision value rather than the raw quotient, so the stored number always equals the one that cycle's latch and warn band decided on. That breaks the type's arithmetic invariant (`(PeakValue, CurrentDrawdownPct)` reconstructable) on exactly those cycles, so `PortfolioRiskState.DrawdownReadingSubstituted` (persisted, `portfolio_risk.drawdown_reading_substituted`) marks them and EVERY operator surface printing the percentage beside the dollar figures must label it — otherwise the percentage and the two dollar amounts silently stop reconciling during exactly the incident a post-mortem would reconstruct. A trusted cycle always writes the exact measurement and clears the marker. A LATCH can never be marked: the floor is clamped to the limit, so a latching `equityDD` is always this cycle's own unclamped measurement — which is why the `/status` latched-drawdown line (`discord_commands.go`) needs no marker and prints no peak/total beside it.

**#1449 review — the warn message labels the arm that can actually latch:** `PortfolioWarningMessageInputs.EquityGuardArmed` mirrors the `equityAvailable && PeakValue > 0` condition the check evaluated for the cycle. Armed ⇒ the #1448 labeling holds (equity owns "distance to kill switch", margin is "from limit"). NOT armed ⇒ the labels SWAP, because the margin arm is the one that flattens the book there — that warn state is reachable, since `portfolioWarnBandSignals` reports `marginInBand` independently of `equityInBand`. On the unarmed path the equity figure is rendered `n/a (guard not armed)` rather than as a stale reading the check did not update, and the trend line omits the equity delta the check forced to 0.

**#1449 review — the cold-start clause's real reach:** the `PeakValue == 0` arm is NOT "a cold-start account that blows up margin on bar 1". Any first cycle with a positive total arms the guard through the ratchet above it, so from that cycle on margin cannot fire the latch. The margin arm on the `equityAvailable` path is reachable only while `totalValue` has been non-positive on EVERY cycle — what `TestCheckPortfolioRisk_PeakZero_MarginCanStillFire` pins with `totalValue = 0`. Margin's standing backstop is the `equityAvailable == false` path plus the #292 breaker.

**#1449 review — `circuit_breaker: false` is the gap this PR must not leave silent:** the #292 per-strategy breaker is opt-outable (#1048) and an explicit `false` suppresses BOTH firing arms (`cbEnabled` gates the drawdown arm and the loss-streak arm), and where it IS enabled the perps `max_drawdown_pct` default is 50 against the portfolio default of 25 — so the handover is to a looser limit, and to none at all when disabled. `recordCircuitBreakerSuppression` therefore also queues a throttled owner DM (`circuit_breaker_suppression_alert.go`): `queueCircuitBreakerSuppressionAlert` under `mu` inside `CheckRisk`, drained by the main loop right after the `CheckRisk` `mu.Unlock()` (#880: no notifier I/O under `mu`) and sent via `formatCircuitBreakerSuppressionDM`. Throttling is INHERITED from the existing `circuitBreakerSuppressedWarned` `LoadOrStore` — one DM per suppression episode, re-armed when the breaker is re-enabled or every threshold clears. Scope is every strategy type, not perps only (futures share the breaker; a spot strategy with it off is equally unhalted). The queue is drained even with no owner configured so it stays bounded.

**#1449 review — warn-DM throttle (`portfolio_warning_throttle.go`):** the warn block is a multi-section message to every channel PLUS an owner DM plus a `RecentTrades` query, and since #1448 a margin reading above the limit no longer ends the band by latching, so the band can persist forever (~144 identical messages/channel/day at the 600s default). `portfolioWarningShouldNotify` (pure) sends on: first cycle of the band; a signal in band now that was NOT in band at the last notification (equity crossing in while margin is throttled is immediate); a rise ≥ `portfolioWarningEscalationPct` (1.0pp) on either lens since the last notification; else the `alert_throttle_interval` floor (default 6h, the `missingMarkAlerts` knob). A suppressed cycle returns the PREVIOUS state unchanged, so the escalation baseline stays anchored to the last reading actually sent (a 0.2pp/cycle creep still fires once it accumulates) and a signal flapping in and out between notifications does not re-arm the newly-in-band hatch. `portfolioWarningAlertsReset()` runs unconditionally whenever `portfolioWarning` is false, so a cleared band — or one ended by the latch — notifies again on its next first cycle. The `RecentTrades` query and message build are skipped on a throttled cycle; the `[WARN]` stdout line and the band-entry `kill_switch_events` append are NOT throttled. `portfolioWarnBandSignals(cfg, prs, equityAvailable)` is the SINGLE definition of warn-band membership — the warn-reason switch inside the risk check and the throttle both call it, so "newly entered the band" means the same thing on both sides. No config field, no schema change, `CurrentConfigVersion` stays 17; `CurrentMarginDrawdownPct` computation/persistence, `planKillSwitchClose` and `AutoResetConfirmedFlatKillSwitch` are untouched. The DM-reset path now routes through `ResetPortfolioKillSwitchManual` (above).

**#1449 review round 3 — the UPWARD direction of an untrusted reading (the mirror of the floor):** the floor closes the fail-open direction only. An untrusted total that UNDERSTATES equity inflates `equityDD`, and that inflated number could latch the portfolio and flatten the whole book — manual and spot included — off a total the same cycle already flagged as substituted or aged (pre-existing on `main`, but it sits on the new floor code and is the one direction the floor leaves open; realistic sources are `sum(member PV)` diverging from the real balance, and a one-generation-stale balance taken just before a deposit or a leveraged win). So the equity arm now gets the same guarantee the floor has: an untrusted measurement alone does not flatten the book on the cycle it appears. **It is a DEFERRAL with a deadline, never a veto** — that distinction is load-bearing, because the two untrusted sources have different lifetimes. `usedStaleRiskBalance` is structurally ONE cycle (the stale branch requires `Generation == generation-1` and does NOT refresh the cache, so a second consecutive miss fails that test, `equityComplete` goes false, and the cycle lands on the `equityAvailable == false` path where margin owns the latch). `usedPVFallback` has NO such bound — `computeTotalPortfolioValue` substitutes `sum(member PV)` for as long as the balance fetch keeps failing and `equityAvailable` stays true throughout — so a straight "only a trusted measurement may latch" rule would leave the portfolio latch disarmed for the whole of a balance-endpoint outage, which is exactly when a genuine crash is least likely to be noticed. The loss that hole permits is unbounded; a spurious flatten costs slippage, fees and a manual reset. The unbounded error governs. Mechanically: `PortfolioRiskState.UntrustedOverLimitSince` (persisted, additive column `portfolio_risk.untrusted_over_limit_since`) stamps the start of an UNBROKEN run of cycles on which an untrusted `equityDD` read above `MaxDrawdownPct`; while `now - since < untrustedEquityLatchDeferral` (15m, a non-configurable safety bound — `CurrentConfigVersion` stays 17) the equity arm is held via `equityLatchDeferred` and the latch does not fire; once the window elapses it DOES fire, with the reason naming the untrusted basis and the escalation. Every non-qualifying cycle clears the window (trusted, at-or-below the limit, or equity guard unarmed), so the clock only ever measures an unbroken run and a one-cycle dip cannot accumulate; the firing latch and all three reset paths clear it too. Persistence is what stops a crash-restart loop from reopening a fresh window forever. `cfg.MaxDrawdownPct <= 0` is excluded, matching the `priorEquityDD` clamp — that degenerate config already means "latch on any drawdown" and keeps its meaning. The margin arm is untouched: on the `equityAvailable == false` path margin still latches immediately, which together with the #292 per-strategy breaker is the standing protection the deferral leans on. **The deferral is loud, not silent:** entering it appends a `latch_deferred` `kill_switch_events` row (once per window, not per cycle), the stdout line moves from `[WARN]` to `[CRITICAL]`, the warn DM BYPASSES the `portfolioWarningShouldNotify` throttle for as long as it is active (the throttle exists so a permanent band cannot spam; silence here would hide the one window in which a manual decision changes the outcome), `BuildPortfolioWarningMessage` replaces the `Distance to kill switch: 0.0% equity` line — which on every other path means a flatten is imminent — with the deferral, its deadline and a pointer at #292, and the `/circuit-breakers` response carries a `Portfolio latch DEFERRED` line. The persisted `CurrentDrawdownPct` on a deferred cycle is the cycle's OWN measurement, unclamped and unmarked: the deferral is recorded in `UntrustedOverLimitSince`, so the operator sees the real number rather than one truncated to the limit. **Test-assertion correction:** the round-2 tests asserted a genuine over-limit measurement latches immediately on an UNTRUSTED cycle. That assertion existed to prove the `priorEquityDD` clamp was not a fail-open, and it is now pinned on a TRUSTED cycle, where the clamp is the only mechanism in play; the untrusted case is pinned as defer-then-escalate in `portfolio_risk_review_1449_deferral_test.go`. Schema changes across the whole #1449 review are two additive columns: `portfolio_risk.drawdown_reading_substituted` and `portfolio_risk.untrusted_over_limit_since`.
